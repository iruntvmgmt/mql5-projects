# D028 Final Report — Multi-Book Portfolio Architecture and Exit-Policy Decisions

Branch `feature/d028-multibook-portfolio`. No merge to `main`. No live
deployment. No entry optimization of A/E/SweepReclaim was performed at any
point in D028. Full stage-by-stage detail, exact numbers, and raw evidence
paths live in `Docs/MultiSpeedZigZag/D028_MULTIBOOK_ARCHITECTURE.md`; this
report is the top-level summary and final decision record.

## 1. What D028 set out to answer

D027 established SweepReclaim as a positive, non-overfit standalone strategy
that shares position ownership with FastMedConfluence under the legacy
single-position-per-symbol architecture, meaning the two compete for the
same slot rather than trading independently. D028's question: does giving
each strategy its own independent, simultaneously-tradeable "book" (separate
physical tickets, separate magics, its own risk allocation, HEDGING account
mode) produce a better system than the shared-ownership legacy, and can
SweepReclaim's exit management be improved without altering its entries?

## 2. Stage-by-stage summary

- **Stage 0 / 0B**: audited and accepted the starting SHA; established a
  corrected legacy shared-ownership baseline (372 trades, +23.0157R,
  PF 1.1253, 25.2798R DD) as the thing independent books must beat.
- **Stages 1-3**: built the independent-book architecture (HEDGING mode,
  per-book magics, own-book-only closing, cross-family close/reversal
  disabled, portfolio risk approval, 2-book/1-per-strategy caps, 0.25%/book
  and 0.50%/portfolio risk limits).
- **Stage 4 (certified, not rerun in this pass)**: proved independent books
  with opposing entries enabled materially outperform shared ownership.
  **P3** (A 2R + SweepReclaim 2R): 343 trades, **+39.9275R**, PF 1.2132,
  23.5883R DD. **P4** (E 3R + SweepReclaim 2R): 331 trades, **+45.9294R**,
  PF 1.2389, 24.2455R DD — the best portfolio found anywhere in D028.
- **Stage 5** (this pass): bounded SweepReclaim exit-policy study, SR0-SR5.
  Found and fixed two real bugs before accepting any result — see §3.
  SR1/SR2 (breakeven, structural trail) REJECTED (worse on every metric,
  negative validation-window expectancy). SR3/SR4 (partial-close variants)
  REDESIGN_REQUIRED — the account's 0.01 minimum lot size makes every
  partial-close attempt clamp back to full size and get skipped, so neither
  mechanism was ever actually exercised (SR3 degenerated byte-identically
  into SR1; SR4 degenerated into a repeated no-op loop with a 40.8R
  drawdown driven by a handful of outliers). SR5 (time stop) was the only
  PORTFOLIO_TEST_ELIGIBLE policy.
- **Stage 6** (this pass): ran SR5 in the actual portfolio (C-A-SR5,
  C-E-SR5) against the P3/P4 controls. **SR5's standalone drawdown
  improvement did not survive contact with the real portfolio** — max DD
  came out exactly identical to P3/P4 in both runs, while cumulative R was
  lower in both (-0.09R and -3.09R). Both REJECTED.

## 3. Two implementation bugs found and fixed during Stage 5 (full detail in the architecture doc)

1. `ProcessBookExitManagement()` only activated in multi-book mode; Stage
   5's single-strategy SweepReclaim configs run in single-book mode, so
   exit management never fired at all for the first SR0-SR5 batch
   (all six variants produced byte-identical results). Fixed the gate to
   cover both modes — provably a no-op for every previously certified
   config (A/E/P1-P4), since FastMedConfluence's exit-policy field is never
   set to anything but the fixed-target default and every pre-Stage-5
   SweepReclaim config also defaults to it.
2. SR5's force-close path wrote a portfolio-journal row immediately, and a
   separate later-bar detection path wrote a second row for the same
   closed ticket. A first fix attempt (gating on book-state identity) was
   wrong and was caught before being accepted — it silently dropped the
   journal row for the much more common own-family-opposite-close case
   instead. The correct fix tracks already-journaled ticket numbers
   explicitly. Verified via exact row-count/hash reconciliation across a
   third full rerun.

Neither bug affected any trading decision, execution logic, or previously
certified number (A/E/P1-P4 numbers are byte-identical before and after
both fixes) — both were confined to secondary CSV export paths and the
newly-added single-book exit-management gate.

## 4. Final architecture decision

**INDEPENDENT_HEDGING_BOOKS_RECOMMENDED**, carrying forward Stage 4's
finding unchanged. Stage 5/6 did not find any exit-policy modification that
improves on **P3 or P4 as already certified in Stage 4** — SR0 (i.e., no
exit-management change to SweepReclaim at all) remains the best-performing
choice. **P4 (FastMedConfluence E 3R + SweepReclaim 2R, both at their
original fixed targets)** is the strongest single portfolio found across
all of D028: 331 trades, +45.9294R, PF 1.2389, 24.2455R DD, positive across
development/validation/holdout.

No SRx exit-management policy is recommended for adoption. SweepReclaim's
exit management should remain exactly as D024/D025/D026/D027 already left
it (structural initial stop, fixed 2R target, own-family opposite exit).

## 5. Anti-overfitting disclosures

- SR1 through SR5 were all tested (5 policies against one control); this
  multiple-comparison exposure is disclosed rather than hidden. Only SR5
  passed Stage 5's screen, and it was then rejected at the portfolio level
  in Stage 6 — the actual outcome of testing five ideas was "none of them
  help," which is itself informative and was not massaged into a positive
  result.
- Every SR1-SR5 threshold (1R activation, 0.5 partial fraction, 48-bar time
  stop) was frozen and documented in `D028_MULTIBOOK_ARCHITECTURE.md`
  **before** any SRx backtest result was inspected.
- Stage 5's robustness checks (top-3-trade removal, best-quarter removal,
  development/validation/holdout split) were applied to every SRx, not only
  the eventual "winner" — this is what caught SR4's extreme outlier
  dependence (+3.49R full-window collapsing to -47.45R with the top 3
  trades removed) before it could be mistaken for a real edge.
- **Gap, disclosed rather than silently skipped**: the handoff's fixed
  predeclared cost/stress scenarios (increased spread, adverse slippage,
  missed fill, delayed stop modification) were **not** run in this pass.
  Given SR5 was ultimately rejected at the portfolio level regardless, this
  gap does not change any decision made here, but it means no D028 result
  has been stress-tested against degraded execution conditions, and that
  should be done before any of D028's certified numbers (P3/P4 included)
  are treated as production-grade rather than research evidence.
- **No D028 result is genuine independent out-of-sample data.** As
  disclosed in D027's own window declaration (carried forward unchanged
  here), this account's usable M5 history begins only three days before
  the existing research window's own start — there is no materially older
  unseen block available. All development/validation/holdout splits in
  D028 are within-sample chronological splits, a real but weaker safeguard
  than genuine OOS data, and every number in this report should be read
  with that caveat.

## 6. What is NOT being recommended

- No SRx exit-management policy (SR1-SR5), for any reason.
- Live trading, of any kind — this remains a research/backtest-only branch.
- Merging to `main`.
- Any change to A's or E's own entry logic (none was made anywhere in D028).
